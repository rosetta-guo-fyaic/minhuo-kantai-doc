# 需求补充材料说明

`02_需求补充材料/` 是一号仓库 `03_需求分析/` 下的正式补充附件区。

本目录用于沉淀已经完成确认、对正式需求分析有重要影响、但不适合直接展开到单条用户故事或完整写入 `03_URD.md` 主体的正式补充分析内容。

## 1. 目录定位

一句话理解：

本目录解决的是“哪些重要分析信息必须正式沉淀下来供后续反复引用，但又不适合直接塞进 `US-*` 或整篇 `03_URD.md` 主体”。

本目录属于正式需求分析真源的一部分，但它不是：

1. 原始调研资料区
2. 待确认事项区
3. 页面或原型设计区
4. 临时草稿堆放区

## 2. 允许存放的内容

允许落入本目录的正式文件，原则上只包括以下五类：

1. 业务规则补充
   - 适用于跨多个 `US-*` 共用的规则、例外规则、计算规则
2. 范围边界说明
   - 适用于项目边界、系统边界、职责边界、本期纳入与不纳入范围说明
3. 角色差异说明
   - 适用于不同角色在同一业务主题下的诉求差异、限制条件或处理口径
4. 术语与口径说明
   - 适用于业务术语、字段口径、统计口径、状态定义等正式说明
5. 历史约束与特殊说明
   - 适用于存量系统兼容、历史流程遗留、组织或政策约束等背景说明

## 3. 禁止存放的内容

以下内容不得进入本目录：

1. 原始访谈记录、调研纪要、结构化转写稿
   - 应留在 `01_需求调研/`
2. 未关闭的待确认事项
   - 应留在 `02_需求确认/01_待确认需求/`
3. 单条用户故事主体内容
   - 应写入 `01_用户故事/US-*.md`
4. 项目级正式总述主体内容
   - 应优先纳入 `03_URD.md`
5. 页面方案、交互设计、原型表达
   - 应进入二号仓库
6. 临时草稿、碎片化备忘、未稳定结论

## 4. 文件命名规则

本目录第一轮不引入新的对象编号体系，统一使用“类型序号 + 主题”的命名方式：

1. `01_业务规则补充_{主题}.md`
2. `02_范围边界说明_{主题}.md`
3. `03_角色差异说明_{主题}.md`
4. `04_术语与口径说明_{主题}.md`
5. `05_历史约束与特殊说明_{主题}.md`

命名原则：

1. 文件名应一眼能看出“文档类型 + 分析主题”
2. 同一主题下避免生成多份语义重叠文件
3. 若已有正式文件，应优先更新，而不是新建相近文件

## 5. 生成门槛

仅当满足以下任一条件时，才建议生成正式需求补充材料：

1. 同一规则影响多个 `US-*`，若分别写入会造成重复
2. 某项边界、口径或历史约束对需求理解很关键，但放进 URD 主体会使主文档过重
3. 某类补充结论已在 `AC-*` 或版本确认层稳定，后续会被持续引用
4. 二号仓库方案设计阶段确定需要反复引用该信息

以下情况不应生成：

1. 仍处于待确认状态
2. 只影响单个用户故事，且在故事正文中可完整表达
3. 本质上属于页面、交互或方案设计内容

## 6. 追溯要求

本目录下每份正式文件，至少必须显式回指以下对象之一：

1. `REQ-*`
2. `US-*`
3. `AC-*`
4. `03_版本需求确认/vX.Y.Z/`

如果无法回指上述任一正式对象，则不应作为正式补充材料落库。

## 7. 与其他目录的关系

### 7.1 与 `01_用户故事/` 的关系

1. `01_用户故事/` 承接单条用户故事的主体内容
2. `02_需求补充材料/` 承接跨故事共用规则、边界、口径和约束
3. 单条故事可在正文中引用本目录文件，但不应以引用代替自身核心描述

### 7.2 与 `03_URD.md` 的关系

1. `03_URD.md` 仍是项目级正式需求分析主文档
2. 本目录用于承接“重要但不宜全文塞入 URD 主体”的正式附件
3. URD 可摘要引用本目录结论，但不应与本目录形成并行主文档

### 7.3 与 `02_需求确认/` 的关系

1. 待确认事项必须先在 `02_需求确认/` 收口
2. 本目录只承接已经确认稳定的正式分析补充内容
3. 禁止把未关闭待确认项直接写成本目录的正式结论

### 7.4 与二号仓库承接的关系

1. 本目录属于 `03_需求分析/` 的正式组成部分
2. 在执行需求分析承接校验时，本目录默认属于正式引用范围
3. 仅正式 `.md` 正文文件可作为直接引用输入；草稿、临时稿和无追溯文件不得进入正式承接范围
