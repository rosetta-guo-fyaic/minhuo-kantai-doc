# 需求确认

`02_需求确认/` 是一号仓库把原始输入转成稳定需求输入的确认控制层。

它的作用不是简单存放几份文档，而是负责把需求对象、待确认事项、确认结果专题和版本冻结范围分开管理，避免未确认信息直接进入 `03_需求分析/`。

## 1. 四类正式产物

本目录建议按以下四类产物理解：

1. `00_需求清单.md`
   - 需求对象总表
   - 记录当前项目所有已识别需求
   - 每条需求都应具备确认状态、版本归属和后续去向
2. `01_待确认需求/02_待确认清单.md`
   - 待确认事项总表
   - 记录哪些需求点还未坐实、为什么未坐实、由谁确认、确认后回写到哪里
3. `02_已确认需求/`
   - 已确认需求专题层
   - 用于按业务域、模块或主题展开复杂确认结果，不替代需求清单主表
4. `03_版本需求确认/`
   - 版本冻结控制层
   - 用于记录某一轮版本范围、冻结口径、差异和确认结论

补充说明：

1. `01_待确认需求/03_业务追问/`
   - 是待确认事项的继续澄清层
   - 用于围绕 `02_待确认清单.md` 中的事项补问、验证和澄清
   - 它不替代待确认主表，也不直接替代正式确认结论
2. `01_待确认需求/04_确认记录/`
   - 是需求确认过程的辅助留痕层
   - 用于沉淀会议确认、访谈确认、回执确认和决策确认的过程与结论
   - 它不替代 `02_待确认清单.md` 主表，但负责为主表回写和正式文档更新提供依据

## 3. 推荐状态流转

建议按以下顺序使用本目录：

1. 原始输入先识别为需求对象，进入 `00_需求清单.md`
2. 无法直接确认的事项，同时进入 `01_待确认需求/02_待确认清单.md`
3. 若基于待确认清单形成进一步追问，先补到 `01_待确认需求/03_业务追问/`
4. 每次发生正式确认动作时，必要时在 `01_待确认需求/04_确认记录/` 下留痕
5. 待确认事项关闭后，回写 `00_需求清单.md`
6. 某一主题确认内容较复杂时，生成 `02_已确认需求/` 下的专题文件
7. 进入版本范围讨论时，再生成 `03_版本需求确认/` 下的版本确认文件

## 4. 使用原则

1. `00_需求清单.md` 管需求对象，不管理全部确认过程细节
2. `02_待确认清单.md` 管确认问题，不替代需求主表
3. `03_业务追问/` 管待确认清单后的澄清动作，不替代待确认主表和正式确认结论
4. `04_确认记录/` 管正式确认过程留痕，不替代待确认主表和正式需求正文
5. `02_已确认需求/` 管复杂确认结果，不替代 URD 和用户故事
6. `03_版本需求确认/` 管版本冻结口径，不替代需求内容本身
7. 未经过本目录确认层的内容，不应直接进入 `03_需求分析/`

## 5. 确认记录生成逻辑

`04_确认记录/` 的文件不是每轮都必须批量生成，但出现以下场景时，建议形成正式确认记录：

1. 某条或某批 `QL-*` 待确认事项通过会议、访谈、回执或决策被正式确认
2. 一次确认动作同时影响多个 `REQ-*`、多个业务规则或多个下游文档
3. 需要保留“为什么这样确认”的过程依据，避免后续只看到结论看不到来路
4. 需要把确认结果同步回写到 `00_需求清单.md`、`02_待确认清单.md`、`AC-*` 或 `03_版本需求确认/vX.Y.Z/`

建议按以下链路理解：

```text
调研结论 / OD 输入冲突
-> 02_待确认清单.md 挂牌
-> 必要时进入 03_业务追问/ 继续澄清
-> 发起正式确认动作
-> 04_确认记录/CR-*.md 留痕
-> 回写 00_需求清单.md 与 02_待确认清单.md
-> 必要时沉淀 AC-* 或 `03_版本需求确认/vX.Y.Z/`
-> 稳定后进入 03_需求分析/
```

确认记录的核心价值，不是重复结论，而是把“确认对象、确认过程、确认结论、回写位置、遗留事项”一次写清。
