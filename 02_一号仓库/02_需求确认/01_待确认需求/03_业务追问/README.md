# 业务追问说明

## 1. 目录定位

`02_需求确认/01_待确认需求/03_业务追问/` 用于承接待确认事项进入正式确认前的继续追问、补问和澄清材料。

它服务的对象，不是全部需求输入，而是已经进入 `02_待确认清单.md` 的待确认事项。

一句话理解：

**先有待确认清单，再围绕待确认事项发起业务追问。**

## 2. 它与其他文件的关系

建议按以下顺序理解：

```text
调研输入 / OD 输入
-> 02_待确认清单.md 挂牌
-> 03_业务追问/ 继续澄清
-> 发起正式确认动作
-> 04_确认记录/CR-*.md 留痕
-> 回写 00_需求清单.md、02_待确认清单.md、AC-*、版本需求确认或 03_需求分析/
```

其中：

1. `02_待确认清单.md`
   - 是待确认事项主表
   - 管“有哪些问题待确认”
2. `03_业务追问/`
   - 是待确认事项的澄清辅助层
   - 管“为了确认这些问题，还需要继续问什么、补什么、验证什么”
3. `04_确认记录/`
   - 是正式确认动作留痕层
   - 管“已经发生了怎样的确认、得出了什么结论、回写到哪里”

## 3. 适用场景

以下场景建议使用本目录：

1. `QL-*` 已经挂牌，但结论不足以直接确认
2. 某条待确认事项仍需补充业务规则、异常场景、角色职责或数据口径
3. 产品经理需要形成结构化追问提纲，再组织访谈、会议或书面回执
4. 需要把追问过程保留为后续确认记录或需求分析的辅助依据

以下内容不建议直接落到本目录：

1. 尚未形成待确认事项的问题草稿
2. 已经完成正式确认的会议纪要
3. 已经稳定、可直接进入 `03_需求分析/` 的正式需求结论

## 4. 生成方式

本目录下的正文文件不在模板仓预置，应在真实项目仓库中按需生成。

建议优先参考：

1. `<TOOL_REPO_ROOT>/07_公共模板库/03_一号仓库模板/06_追问清单模板.md`
2. `<TOOL_REPO_ROOT>/08_AI工作站/01_AI能力模块/03_一号仓库能力模块/AM-01_需求分析器.md`

常见命名方式可按主题或批次组织，例如：

1. `QF-01_{主题}业务追问.md`
2. `QF-02_{主题}业务追问.md`

若项目已有统一编号规则，也可以沿用项目内规则，但应确保能回指对应 `QL-*`。

## 5. 使用原则

1. 业务追问必须回指 `02_待确认清单.md` 中的对应事项，不能脱离主表单独存在。
2. 业务追问用于澄清和验证，不直接替代正式确认结论。
3. 追问完成后，应根据结果决定是继续补问、发起正式确认，还是直接回写关闭。
4. 如果追问结果已经形成正式确认动作，应进一步沉淀到 `04_确认记录/CR-*.md`。
5. 若追问后仍存在遗留问题，应继续保留在 `02_待确认清单.md` 中挂牌，而不是默认关闭。
