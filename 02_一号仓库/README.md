# 一号仓库

## 1. 仓库定位

`02_一号仓库/` 是项目需求输入、需求调研、需求确认和需求分析主仓。

它主要负责三件事：

1. 承接 OD 输出的业务原始需求输入与产品经理补充调研输入
2. 对需求进行确认、追问、收口和版本确认
3. 在进入二号仓库前，形成可被正式设计承接的需求分析结果

一句话理解：

**一号仓库负责把需求调清、确认清、分析清。**

## 2. 当前结构

```text
02_一号仓库/
├── README.md
├── .claude/
├── .agents/
├── 01_需求调研/
├── 02_需求确认/
└── 03_需求分析/
```

各目录职责如下：

- `01_需求调研/`
  - 承接原始资料、问卷、访谈、调研记录和结构化整理稿
- `02_需求确认/`
  - 承接待确认需求、业务追问、需求清单、已确认需求、版本需求确认和版本需求变更确认
- `03_需求分析/`
  - 承接正式需求分析产物，包括需求管理总览、用户故事、需求补充材料和 URD

补充说明：

1. `02_需求确认/00_需求清单.md`
2. `03_需求分析/00_需求管理总览.md`
3. `03_需求分析/03_URD.md`

以上三类正文文件不预置在模板仓中。  
它们应在真实项目仓库初始化后，由对应 Skill 基于 `<TOOL_REPO_ROOT>/07_公共模板库/03_一号仓库模板/` 下的模板文件和项目实际需求内容正式生成。

其中：

- `<PROJECT_ROOT>/00_OD工作区/`
  - 是一号仓库外部的上游业务输入源
- `<PROJECT_ROOT>/02_一号仓库/01_需求调研/`
  - 是一号仓库内部的补充调研输入层
- `<PROJECT_ROOT>/02_一号仓库/02_需求确认/`
  - 是 OD 输入与产品调研输入的正式合流确认层

## 3. 上游输入关系

一号仓库当前有两类上游输入：

1. `<PROJECT_ROOT>/00_OD工作区/`
   - OD 输出的业务原始需求输入
2. `<PROJECT_ROOT>/02_一号仓库/01_需求调研/`
   - 产品经理补充形成的调研输入

这两类输入都不直接替代正式需求分析真源，而是共同进入 `<PROJECT_ROOT>/02_一号仓库/02_需求确认/`。

## 4. 真源使用顺序

一号仓库建议按以下顺序理解和使用：

### 4.1 OD 输入层

- 以 `<PROJECT_ROOT>/00_OD工作区/` 为业务原始需求输入层
- 这里解决“项目方法论输入、流程、组织、权限、字典的上游输入从哪里来”

### 4.2 需求调研层

- 以 `<PROJECT_ROOT>/02_一号仓库/01_需求调研/` 为调研输入层
- 这里解决“产品经理补充资料从哪里来、调研怎么做、补充信息如何整理”

### 4.3 需求确认层

- 以 `<PROJECT_ROOT>/02_一号仓库/02_需求确认/` 为需求确认层
- 这里解决“OD 输入与产品调研输入如何合并、哪些需求待确认、哪些已确认、版本范围如何确认”

### 4.4 需求分析层

- 以 `<PROJECT_ROOT>/02_一号仓库/03_需求分析/` 为正式需求分析层
- 进入二号仓库的正式输入，仍应以该目录为主

## 5. 当前工作链路

一号仓库建议按以下链路推进：

```text
OD业务原始需求输入
+ 产品补充调研输入
-> 需求确认
-> 需求分析
-> 移交二号仓库
```

展开后通常表现为：

```text
<PROJECT_ROOT>/00_OD工作区/
+ <PROJECT_ROOT>/02_一号仓库/01_需求调研/
-> 调研记录（SRV-*）
-> 业务追问与待确认事项（QL-*）
-> 需求清单（REQ-*）
-> 确认记录（CR-*）
-> 已确认需求专题（AC-*）
-> 版本需求确认（按 `vX.Y.Z/` 建目录）
-> 用户故事
-> URD
-> 移交二号仓库
```

## 6. 常见任务与落点映射

前置说明：

1. OD 提供的项目方法论输入、To-Be 流程、组织分工、权限矩阵、字典输入
   - 不直接写入 `03_需求分析/`
   - 应先由 `od-demand-analyzer` 解析并承接到 `02_需求确认/`
2. 产品经理新增的访谈、问卷、附件、调研结论
   - 落到 `01_需求调研/`
3. 两类输入收口后形成 `REQ-*` 主表、`QL-*` 主表及必要的确认留痕
   - 落到 `02_需求确认/`

1. 原始附件接收与保真存档
   - 落到 `01_需求调研/01_原始资料/`
2. 调研问卷设计与访前准备
   - 落到 `01_需求调研/02_需求问卷/`
3. 调研纪要、访谈记录和现场记录
   - 落到 `01_需求调研/03_调研记录/`
4. 原始资料转写、整理和结构化分析
   - 落到 `01_需求调研/04_调研整理（md）/`
5. 从调研进入确认前的初步结论和待转确认项
   - 落到 `01_需求调研/05_调研结论与待转确认项/`
6. 业务追问、待确认问题和确认记录
   - `QL-*` 主表落到 `02_需求确认/01_待确认需求/02_待确认清单.md`
   - 业务追问与其他辅助材料优先落到 `02_需求确认/01_待确认需求/03_业务追问/`
   - `CR-*` 正式确认记录落到 `02_需求确认/01_待确认需求/04_确认记录/`
7. 需求清单主表
   - 在真实项目仓库中生成 `REQ-*` 主表，并落到 `02_需求确认/00_需求清单.md`
8. 已确认需求的专题沉淀
   - 生成 `AC-*` 文件并落到 `02_需求确认/02_已确认需求/`
9. 版本范围、版本确认和需求冻结说明
   - 在真实项目仓库中，按 `vX.Y.Z/` 建目录
   - 至少形成：
     - `00_版本需求清单.md`
     - `01_版本需求变更确认.md`（仅在后续发生正式版本范围变更时，由人工补充，不得由 AI 自动编造）
10. 需求管理总览、用户故事、需求补充材料和 URD
   - 在真实项目仓库中生成并落到 `<PROJECT_ROOT>/02_一号仓库/03_需求分析/`
11. 需求分析结果承接到二号仓库方案设计阶段
   - 二号仓库 `<PROJECT_ROOT>/03_二号仓库/01_方案设计/` 直接读取 `<PROJECT_ROOT>/02_一号仓库/03_需求分析/` 下的正式真源
   - 不再创建或维护二号仓库 `03_需求分析/` 镜像目录

要特别避免两种混用：

1. 把 `01_需求调研/` 中的原件或整理稿直接当正式分析结论使用。
2. 把 `<PROJECT_ROOT>/00_OD工作区/` 的输入或 `<PROJECT_ROOT>/02_一号仓库/02_需求确认/` 中尚未完成分析建模的确认材料，直接当二号仓库正式设计真源使用。

1. `03_版本需求确认/vX.Y.Z/00_版本需求清单.md`
   - 是当前版本进入二号仓库前的正式需求确认真源
2. `03_版本需求确认/vX.Y.Z/01_版本需求变更确认.md`
   - 只用于记录该版本需求确认完成以后，又发生的正式版本范围变更
   - 必须由产品经理和业务方人工确认形成

4. 若变化已经明显超出当前版本目标，准备进入下一版本
   - 应先回到零号仓库建立新版本身份
   - 再在一号仓库建立新的 `vX.Y.Z/00_版本需求清单.md`

## 8. 原型边界

一号仓库不生成简单原型，也不承接临时页面表达。

若需求仍需通过页面、交互或菜单结构进一步确认，应在进入二号仓库后，由正式方案设计和原型设计阶段承接。

## 9. 推荐正式产物

一号仓库建议至少形成以下正式产物：

1. 调研整理稿
2. 调研记录（`SRV-*`，用于过程留痕与来源追溯）
3. 业务追问与待确认清单（`QL-*`）
4. 需求清单（`REQ-*` 主表）
5. 确认记录（`CR-*`）
6. 已确认需求专题（`AC-*`，按需生成）
7. 版本需求确认记录（`03_版本需求确认/vX.Y.Z/`）
8. 用户故事
9. URD

## 10. 与 OD 工作区的关系

1. `<PROJECT_ROOT>/00_OD工作区/` 是一号仓库的重要上游输入源。
2. 其内容包括项目方法论输入、To-Be 流程、组织分工、权限矩阵和字典。
3. 这些内容不直接进入 `<PROJECT_ROOT>/02_一号仓库/03_需求分析/`，而是先进入 `<PROJECT_ROOT>/02_一号仓库/02_需求确认/`。
4. 产品经理补充形成的 `<PROJECT_ROOT>/02_一号仓库/01_需求调研/` 内容，也同样进入 `<PROJECT_ROOT>/02_一号仓库/02_需求确认/`。
5. 因此 `<PROJECT_ROOT>/02_一号仓库/02_需求确认/` 是 OD 输入与产品调研输入的正式合流层。

## 11. 与二号仓库的交接关系

一号仓库向二号仓库提供的，不是“所有问题都已解决”的材料，而是“已具备进入正式设计阶段的需求分析输入”。

二号仓库正式承接的上游仍然是：

1. 真实项目仓库中生成的 `03_需求分析/00_需求管理总览.md`
2. `03_需求分析/01_用户故事/`
3. `03_需求分析/02_需求补充材料/`
4. 真实项目仓库中生成的 `03_需求分析/03_URD.md`
5. 以上内容由二号仓库 `01_方案设计/` 直接引用，作为方案设计阶段的正式承接输入

## 12. 进入二号仓库前的最小门禁

进入二号仓库前，建议至少确认：

1. OD 输入与产品调研输入已完成本轮合流确认
2. 原始业务输入已完成调研整理
3. 待确认需求已显式登记并完成本轮必要追问
   - 至少应在 `02_需求确认/01_待确认需求/02_待确认清单.md` 中形成主清单
4. 已发生正式确认动作的事项，已形成对应 `CR-*` 确认记录，并完成主表回写
5. 需求清单已形成，并区分待确认与已确认状态
6. 复杂确认结果如已稳定，必要时已沉淀为 `AC-*`
7. 版本范围已完成需求确认，必要时已形成 `03_版本需求确认/vX.Y.Z/`
   - 若属于基线后正式变更，已存在人工确认的 `01_版本需求变更确认.md`
8. 用户故事和 URD 已形成正式版本
9. 关键对象、状态、权限和术语已具备进入设计阶段的最小清晰度

## 13. 强制边界

- 一号仓库不是正式产品方案设计主仓
- 不承载正式页面真源、PRD 真源、研发实现和运维交付正文
- 不把 `<PROJECT_ROOT>/00_OD工作区/` 的输入直接当成正式需求分析真源
- 不用大量未整理原件直接替代正式需求分析结论
- 未确认信息不得直接写成正式方案事实
- `03_需求分析/` 中的正式文档，不应写成轻量占位稿
