# 产品原型说明

## 1. 目录定位

`02_产品原型/` 是二号仓库的页面设计真源层。

它负责把 `01_方案设计/` 中已经稳定的业务方案真源，落成可进入 HTML / Vue 表达层和 `05_产品需求/` 的页面真源。

本目录负责定义：

1. 系统级原型总览。
2. 系统菜单与导航真源。
3. 全局对象总览与逐对象主定义。
4. 全局页面交互与显隐约定。
5. `FR -> PD` 页面承接关系。
6. 全局规则状态承接。
7. 模块级对象、规则、权限、异常承接。
8. 模块级页面边界、页面关系与页面映射。
9. 页面级正式设计文档。
10. 原型真源闭环检查结论。

它不负责：

1. 直接裁决业务方案边界。
2. 单独替代 HTML / Vue 原型展示层。
3. 主定义系统级护栏、系统级权限、非功能需求或集成需求。
4. 直接替代 PRD、护栏设计或产品基线。
5. 在版本范围仍未稳定时，替代一号仓库或零号仓库裁决版本归属。

一句话理解：

**原型层负责定义页面事实，但不替代 PRD 层收口页面之外的交付事实。**

## 4. 使用顺序

建议按以下顺序阅读和维护：

1. 先读取 `01_方案设计/` 的正式输入。
2. 先建立 `00_原型设计总览.md` 中的页面清单、页面类型和模块分布。
3. 再建立 `00-1_系统菜单设计.md`。
4. 再建立 `01_全局对象模型总览.md` 与 `01_全局对象模型/`。
5. 再建立 `02_全局页面交互与显隐约定.md`。
6. 再建立 `03_PD桥接总表.md`、`04_模块页面映射表.md` 和 `05_全局规则状态承接总表.md`。
7. 再按模块补 `MODxx-模块名/00_模块原型总览.md` 与 `01_模块页面关系与导航设计.md`。
8. 再按模块补 `02_模块对象与字段承接.md`、`03_模块规则状态承接.md`、`04_模块权限显隐承接.md`、`05_模块异常与闭环承接.md`。
9. 再逐页补 `PD-*` 页面设计文档。
10. 如存在页面归属或跨模块跳转冲突，再进入 `99_跨模块原型裁决与冲突处理/`。
11. 再完成 `00_原型真源闭环检查.md`。
12. 默认先驱动 `03_HTML原型/`。
13. 如需 URL 化演示、复杂交互验证或前端联调预演，再补 `04_Vue原型/`。

这里要特别区分三件事：

1. 原型真源建设
   - 目标是把当前版本候选范围设计成稳定的页面真源
2. 版本范围确认
   - 目标是确认“这些页面和功能是否真的纳入当前版本”
   - 由一号仓库与零号仓库主控
3. 产品基线或基线后正式变更
   - 目标是冻结当前版本，或对已冻结版本形成正式变更留痕
   - 不属于本目录普通页面迭代动作

补充要求：

1. 原型阶段所有输出都要为下游系统级表达做准备，不允许把“单页草图”误当成正式原型完成状态。
2. 后续进入 `03_HTML原型/` 或 `04_Vue原型/` 时，目标都应是生成高可用、高保真、可点击、可操作的系统原型。
3. 因此，本目录中的页面类型、动作闭环、显隐分析、菜单归属和返回路径，不得从简、省略或留成模糊口径。

5. `FR -> PD -> HTML/Vue` 页面承接关系，以 `03_PD桥接总表.md` 为准。
6. 模块与页面的聚合视图，以 `04_模块页面映射表.md` 为准。
7. 模块页面范围、模块页面分组和模块承接状态，以 `MODxx-模块名/00_模块原型总览.md` 为准。

11. HTML 与 Vue 原型只负责表达，不得反向定义新的页面事实。
12. 页面标题、错误提示、导出命名等动态内容，原型真源应优先表达业务语义，不应直接保留模板变量名。

## 5.1 原型阶段与版本治理边界

本目录与版本治理的边界，建议按以下方式理解：

1. 本目录负责把“当前版本候选范围”落为页面真源。
2. 本目录不负责裁决“当前版本是否正式冻结”。
3. 若在原型阶段发现：
   - 页面是否纳入当前版本仍未裁决
   - 页面拆分、菜单归属或实体口径变化已经影响版本边界
   - 当前变化本质上已属于下一版本
   应先回一号仓库或零号仓库处理，不应继续把它写成“当前版本原型已稳定”。
4. 若当前版本已经冻结，后续正式变化不得伪装成本目录中的普通原型迭代，应改走产品基线正式变更链路。

## 5.2 原型层与 PRD 层的边界

本目录与 `05_产品需求/` 的边界，建议按以下方式理解：

1. 页面结构、页面动作、页面显隐、页面去向和页面返回闭环，以本目录为准。
2. 页面之外但交付必须明确的内容，如系统级护栏、系统级权限、非功能需求、集成约束、研发测试消费口径，以 `05_产品需求/` 为准。
3. `05_产品需求/` 在生成时，必须同时学习本目录和 `01_方案设计/`，不得绕过页面真源独立定义交付事实。
4. 若某项内容无法在页面真源中完整表达，但又影响正式交付，应在本目录明确“原型已承载部分”和“仍由 PRD 承载部分”的边界，而不是把全部内容强压进 `PD-*`。

## 6. 菜单合法性规则

菜单设计必须遵循 `<TOOL_REPO_ROOT>/06_工作规范/05_产品设计规范/02_菜单与导航设计规范.md`。

原型阶段默认执行以下规则：

1. 只有列表页、报表页、驾驶舱页允许作为菜单页。
2. 详情页、简单表单页、复杂表单页、弹窗页、抽屉页默认不得挂菜单。
3. 非菜单页必须明确归属菜单页。
4. 非菜单页必须明确来源入口和返回路径。
5. 若页面不符合菜单挂载合法性，不得进入 HTML / Vue 表达层。

## 6.1 页面类型判定原则

页面类型应由 AI 先根据上游方案事实完成自判，不应默认要求产品经理逐页手工选择。

默认判定顺序如下：

1. 先判断是否为菜单页候选。
2. 再判断主职责属于列表、表单、详情、报表还是驾驶舱。
3. 若判定为表单页，再细分为简单表单页或复杂表单页。
4. 若页面同时具备多类特征，按主职责裁决，不按界面上出现了多少组件裁决。
5. 只有在主职责冲突、上游事实不足或页面可能需要拆页时，才升级请产品经理确认。

补充规则如下：

1. 若页面已存在 `PD-*`，后续再生成该页面时，应直接继承 `PD-*` 中的页面类型判定与裁决，不得重新判型。
2. 若页面尚未形成 `PD-*`，但 `00_原型设计总览.md`、`MODxx-模块名/00_模块原型总览.md` 或 `00-1_系统菜单设计.md` 已有稳定结论，应优先继承这些真源。
3. 只有在上述真源均不存在时，才启动 AI 自判。
4. 页面类型一旦落入正式真源，后续 HTML / Vue 表达层必须消费该结论，不得脱离真源私自改型。

## 7. 页面动作与显隐规则

所有页面都必须遵循 `<TOOL_REPO_ROOT>/06_工作规范/05_产品设计规范/03_原型设计与交互规范.md`。

原型阶段默认执行以下规则：

1. 页面上的按钮、文本链接、操作列、卡片入口、页签、图表下钻、弹窗触发器，均必须完成动作闭环设计。
2. 所有跳转类动作都必须明确：来源位置、目标页面或结果态、参数传递方式、返回路径。
3. 所有页面都必须完成字段、按钮、页签、卡片、图表、批量操作、导入导出入口的显示 / 隐藏 / 禁用必要性分析。
4. 显隐分析必须至少从角色、状态、权限、数据条件、业务场景五个维度展开。
5. 不允许为了从简而默认全部展示，也不允许只写静态按钮外观而不设计动作结果。

## 9. 强制边界

1. 不得用原型页面或表达层页面，反向裁决业务边界、业务状态、跨模块规则、权限主口径或版本归属。
2. 不得跳过 `00_原型设计总览.md`、`00-1_系统菜单设计.md`、`01_全局对象模型总览.md` 与 `01_全局对象模型/` 直接批量生成 `PD-*`。
3. 不得在 `PD-*` 中散落系统级护栏、系统级权限、非功能需求或版本治理结论，而不回写正式归属目录。
4. 不得把 HTML / Vue 的限制直接当成页面真源事实；如限制影响正式事实，必须回流本目录。
5. `MODxx-模块名/00_模块原型总览.md` 属于原型模块说明，不替代 `05_产品需求/` 下的模块需求说明。
6. 原型阶段若发现页面无法独立承载的系统级内容，应明确标注“由 PRD 承接”，而不是强行在页面正文中补写。
7. 不得把系统设计里的所有内容都压进页面真源；只有与页面设计直接相关的内容，才完全由本目录承载。
