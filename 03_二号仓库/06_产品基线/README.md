# 产品基线说明

## 1. 目录定位

`06_产品基线/` 用于存放各正式版本冻结后的产品基线快照、版本范围说明和基线后需求变更记录。

它负责沉淀：

1. 当前版本正式冻结口径
2. 当前版本完整产品原型快照
3. 当前版本完整产品需求快照
4. 当前版本正式需求范围
5. 当前版本基线后正式需求变更

补充理解：

1. 若是上一版本完成后进入下一版本，本目录负责形成“新版本完整基线”。
2. 若是当前版本已经冻结后又发生正式变化，本目录负责形成“基线后正式变更留痕”。
3. 若是当前已冻结或已发布版本的小范围修复，本目录仍通过正式变更链路留痕，但是否进入 `hotfix/vX.Y.Z`，应结合版本治理规则判断。

## 1.1 固定正式产物

本目录的正式产物以“版本目录 + 完整快照 + 范围说明”的方式承接。

目录级骨架示意如下：

```text
03_二号仓库/
└── 06_产品基线/
    ├── v1.0.0/
    │   ├── 01_产品原型/
    │   ├── 02_产品需求/
    │   └── 03_需求范围/
    │       ├── 00_版本范围说明.md
    │       ├── 01_版本需求清单.md
    │       └── 需求变更/
    ├── v1.1.0/
    │   ├── 01_产品原型/
    │   ├── 02_产品需求/
    │   └── 03_需求范围/
    │       ├── 00_版本范围说明.md
    │       ├── 01_版本需求清单.md
    │       └── 需求变更/
    └── README.md
```

## 1.2 基线文档的生成逻辑

| 正式文档 | 生成时点 | 直接输入 | 作用定位 |
|------|------|------|------|
| `vX.Y.Z/01_产品原型/` | 当前版本冻结时 | `02_产品原型/` 下正式页面真源 | 保存当前版本完整原型快照 |
| `vX.Y.Z/02_产品需求/` | 当前版本冻结时 | `05_产品需求/` 下正式需求真源 | 保存当前版本完整需求快照 |
| `vX.Y.Z/03_需求范围/00_版本范围说明.md` | 当前版本冻结时 | 零号仓库版本总表与版本卡 + 一号仓库版本需求确认 + 当前版本设计结果 | 解释当前版本相对上一版本的范围承接 |
| `vX.Y.Z/03_需求范围/01_版本需求清单.md` | 当前版本冻结时 | 零号仓库版本总表与版本卡 + 一号仓库版本需求确认 + 当前版本设计结果 | 固定当前版本设计冻结范围 |
| `vX.Y.Z/03_需求范围/需求变更/` | 产品基线冻结后 | 正式变更确认结果 | 记录基线后正式需求变更 |

### 1.2.1 产品原型快照的固定承接范围

`vX.Y.Z/01_产品原型/` 不是只复制若干 `PD-*` 页面，而是要冻结当前版本完整的页面真源体系。

至少应包含：

1. `00_原型设计总览.md`
2. `00-1_系统菜单设计.md`
3. `01_全局对象模型总览.md`
4. `01_全局对象模型/`
5. `02_全局页面交互与显隐约定.md`
6. `03_PD桥接总表.md`
7. `04_模块页面映射表.md`
8. `05_全局规则状态承接总表.md`
9. `00_原型真源闭环检查.md`
10. `MODxx-模块名/00_模块原型总览.md`
11. `MODxx-模块名/01_模块页面关系与导航设计.md`
12. `MODxx-模块名/02_模块对象与字段承接.md`
13. `MODxx-模块名/03_模块规则状态承接.md`
14. `MODxx-模块名/04_模块权限显隐承接.md`
15. `MODxx-模块名/05_模块异常与闭环承接.md`
16. `MODxx-模块名/PD-xxx_*.md`
17. `99_跨模块原型裁决与冲突处理/*.md`

说明：

1. 若某模块已纳入当前版本范围，该模块对应的模块原型总览、模块页面关系与页面真源必须一并快照。
2. 不得只冻结页面文件而遗漏菜单设计、页面桥接关系、模块页面映射和原型闭环检查，否则后续无法解释页面归属与页面承接链。
3. `03_HTML原型/` 与 `04_Vue原型/` 属于表达层，可按需要随基线附带归档，但不替代 `01_产品原型/` 中的正式页面真源快照。

### 1.2.2 产品需求快照的固定承接范围

`vX.Y.Z/02_产品需求/` 不是只复制若干 `FR-*` 文件，而是要冻结当前版本完整的 PRD 真源体系。

至少应包含：

1. `00_产品需求总览.md`
2. `01_全局需求.md`
3. `02_护栏设计.md`
4. `03_权限矩阵.md`
5. `04_FR-PD追溯总表.md`
6. `05_全局对象与状态实现口径.md`
7. `06_全局异常与结果态总表.md`
8. `MODxx-模块名/00_模块需求说明.md`
9. `MODxx-模块名/01_模块领域模型与流程承接.md`
10. `MODxx-模块名/02_模块规则状态与护栏承接.md`
11. `MODxx-模块名/03_模块页面动作与权限承接.md`
12. `MODxx-模块名/FR-xxx_*.md`
13. `99_PRD汇编阅读版.md`

说明：

1. `99_PRD汇编阅读版.md` 不是事实裁决真源，但建议随版本一并归档，方便产品经理按版本阅读和验收。
2. 阅读版可以归档，但默认不得作为三号仓库主消费输入。
3. 不得只冻结 `FR-*` 而遗漏 `00_产品需求总览.md`、`04_FR-PD追溯总表.md`、模块需求说明和全局约束，否则无法稳定说明当前版本的完整交付口径。
4. 若某些全局文件尚未形成正式口径，不得提前进入产品基线冻结。

补充说明：

1. 若是首个正式版本，例如 `v1.0.0`
   - 可不要求存在上一版本基线快照
   - `00_版本范围说明.md` 应说明“本版本为首个正式基线版本”
2. 若是后续版本，例如 `v1.1.0`
   - 应以前一版本基线作为承接基准
3. 若是基线后正式变更
   - 必须先存在一号仓库人工确认的 `01_版本需求变更确认.md`
   - 再在本目录中形成 `CHG-*`

## 2. 使用规则

1. 当前版本目录中的完整快照是当前版本最终口径，不应被临时说明替代
2. 已进入基线目录的内容，如需调整，应先回到过程文档修订，再按正式变更流程回写
3. 当前版本目录应能追溯到 `01_方案设计/`、`02_产品原型/`、`05_产品需求/`
4. `03_需求范围/` 必须明确写出“本次未纳入范围”，避免冻结口径与待定范围混淆
5. 原型快照必须同时保留页面、菜单、桥接表、模块映射和模块导航关系，不能只保留页面正文
6. PRD 快照必须同时保留全局真源、追溯总表、模块需求说明和功能正文，不能只保留功能正文
7. 阅读件、待办件、说明件可以归档，但不得冒充正式主真源进入下游消费链

## 2.1 三类场景的边界

在使用本目录前，应先判断当前属于哪一类场景：

1. 新版本承接
   - 例如 `v1.0.0` 完成后开始做 `v1.1.0`
   - 目标是形成新的 `vX.Y.Z/` 完整快照
2. 基线后正式变更
   - 当前版本已冻结，之后又发生正式需求变化
   - 目标是在当前版本 `03_需求范围/需求变更/` 下形成 `CHG-*`
3. `hotfix`
   - 属于基线后正式变更中的修复型承接
   - 除在本目录留痕外，还要进一步判断是否在 `hotfix/vX.Y.Z` 分支上承接

反向排除规则：

1. 基线冻结前的正常方案收口、原型细化、PRD 补全
   - 不属于本目录的正式变更
2. 下一版本的正常设计承接
   - 不得写成上一版本的 `CHG-*`

## 2.2 进入本目录前的最小前置

进入 `06_产品基线/` 前，至少应满足：

1. `05_产品需求/00_产品需求总览.md` 已形成
2. `02_产品原型/00_原型设计总览.md`、`00-1_系统菜单设计.md`、`03_PD桥接总表.md`、`04_模块页面映射表.md` 已形成
3. 本轮范围内 `02_产品原型/MODxx-模块名/00_模块原型总览.md`、`01_模块页面关系与导航设计.md` 与 `PD-*.md` 已达到定稿或准定稿状态
4. 本轮范围内 `05_产品需求/MODxx-模块名/00_模块需求说明.md` 与 `FR-*.md` 已达到定稿或准定稿状态
5. `05_产品需求/01_全局需求.md`、`02_护栏设计.md`、`03_权限矩阵.md`、`04_FR-PD追溯总表.md` 已形成
6. `01_零号仓库/04_产品路标/00_版本总表.md` 与当前版本 `VER-vX.Y.Z_版本卡.md` 已形成并锁定当前版本口径
7. `02_一号仓库/02_需求确认/03_版本需求确认/vX.Y.Z/` 已形成当前版本正式需求确认结果
8. 本轮纳入范围已明确，不存在关键功能是否纳入的未裁决争议
9. 上游方案、原型、PRD 的追溯链完整
10. 若是基线后正式变更，已存在一号仓库人工确认的 `01_版本需求变更确认.md`

首个版本补充说明：

1. 若当前是首个正式版本
   - 可以不存在上一版本基线目录
   - 但零号仓库版本身份和一号仓库版本需求确认结果仍必须齐备

## 2.3 冻结顺序

建议按以下顺序执行基线冻结：

1. 先确认本轮正式输入清单
2. 再确认零号仓库当前版本口径与一号仓库版本需求确认结果
3. 再确认模块和功能纳入范围
4. 再确认明确排除范围
5. 再确认全局需求、护栏和权限口径
6. 再生成对应版本目录下的完整快照与范围说明
7. 后续若有基线后正式变更，应进入 `03_需求范围/需求变更/`，不得直接覆盖旧口径

若是基线后正式变更，建议按以下顺序执行：

1. 先确认一号仓库已形成 `01_版本需求变更确认.md`
2. 再确认本次变化属于当前版本正式变更，而不是下一版本新增范围
3. 再判断是否属于修复型变更，是否建议走 `hotfix/vX.Y.Z`
4. 再生成 `CHG-*`
5. 最后判断是否需要同步更新完整快照和范围说明

## 2.4 强制边界

1. 本目录只冻结已确认事实，不重新定义方案、原型或 PRD 主内容
2. 本目录不得替代 `FR-*`、`PD-*`、`USS-*` 等过程真源
3. 若过程真源仍存在关键空缺，不应提前生成正式基线目录
4. 基线一旦冻结，不应用临时说明、聊天结论或待办记录直接改写
5. `需求变更/` 只记录基线后正式变更，不记录基线前正常设计收口
6. 不得把新版本承接写成上一版本 `需求变更/CHG-*`
7. 不得在缺少人工确认变更真源时，直接落库基线后正式变更
8. 不得把 `99_*` 阅读件、待办件或说明件当作三号仓库正式输入主真源
