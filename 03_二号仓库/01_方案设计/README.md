# 方案设计说明

## 1. 目录定位

`01_方案设计/` 是二号仓库的方案真源层。

本目录负责把一号仓库已经稳定的正式需求输入，收口为可进入原型设计和产品需求阶段的产品方案真源。

当前阶段采用的正式结构为：

```text
03_二号仓库/
└── 01_方案设计/
    ├── 00_产品解决方案总览.md
    ├── 01_产品功能清单.md
    ├── 02_全局方案定义/
    │   ├── 01_全局状态与生命周期定义.md
    │   ├── 02_全局业务规则定义.md
    │   ├── 03_全局业务实体关系与属性口径定义.md
    │   ├── 04_全局字典与枚举定义.md
    │   ├── 05_全局角色权限与数据范围定义.md
    │   ├── 06_全局导航与模块协同定义.md
    │   └── 07_全局集成与外部协同定义.md
    ├── 03_FR桥接总表.md
    ├── 04_模块功能映射表.md
    ├── MOD01-模块名/
    │   ├── 00_模块方案总览.md
    │   ├── 01_用户故事方案/
    │   │   ├── USS-001_故事名.md
    │   │   └── ...
    │   ├── 02_模块业务流程与场景设计.md
    │   ├── 03_模块业务规则与状态设计.md
    │   ├── 04_模块业务实体与属性设计.md
    │   ├── 05_模块权限与角色设计.md
    │   ├── 06_模块导航与页面方向设计.md
    │   └── 07_模块异常与闭环设计.md
    ├── MOD02-模块名/
    └── 99_跨模块设计与冲突处理/
        ├── 00_全局裁决记录.md
        └── 01_跨模块冲突清单.md
```

说明：

1. 在 `00_项目仓库模板/` 中，本目录应保留必要子目录骨架与各级 `README.md`，但不预置任何正式正文。
2. `02_全局方案定义/` 与 `99_跨模块设计与冲突处理/` 应作为真实项目仓库的默认子目录存在。
3. `MODxx-模块名/` 应在真实项目仓库中按需创建，不在模板仓库中预置具体模块目录。
4. 上述正式文档应在真实项目仓库中，由产品经理或 `AM-02 / sol-design Skill` 按需生成。

## 2. 本目录负责什么

本目录负责定义：

1. 项目级产品解决方案总览。
2. 模块级完整方案设计。
3. 单个用户故事的来源追溯与细粒度方案分析。
4. 跨模块的全局状态、规则、实体、属性、字典、权限和导航协同。
5. 从故事方案、模块方案到原型、PRD 的根层功能桥接关系。
6. 跨模块设计冲突和正式裁决记录。

它不负责：

1. 存放一号仓库需求分析正文副本。
2. 直接产出正式页面设计真源或 HTML / Vue 原型。
3. 直接产出正式 `FR-*` 正文、护栏设计、权限矩阵和产品基线。
4. 在版本范围仍未稳定时，替代一号仓库或零号仓库裁决版本归属。

## 3. 每类正式文档的生成逻辑

| 正式文档 | 生成时点 | 直接输入 | 作用定位 |
|------|------|------|------|
| `00_产品解决方案总览.md` | 方案阶段启动时先建立骨架，模块与故事稳定后持续回写 | 一号仓库正式输入、模块划分、范围说明 | 管理模块索引、协作分工、进度状态、门禁结论 |
| `MODxx-模块名/` | 模块边界明确后启动 | 正式 `US / URD / 需求补充材料 / OD输入` | 模块级正式方案真源 |
| `MODxx-模块名/01_用户故事方案/USS-*.md` | 单个故事需要来源追溯和细粒度设计时 | 对应故事输入及其上下文 | 模块方案包内的细粒度设计单元 |
| `02_全局方案定义/*.md` | 多个模块方案已形成并开始收口共性时 | 全部模块方案包 | 裁决跨模块共性口径 |
| `01_产品功能清单.md` | 模块方案稳定并可识别功能点时 | 模块方案、全局方案定义 | 建立功能点总览、版本范围与桥接范围 |
| `03_FR桥接总表.md` | 功能点需要明确下游承接关系时 | 模块方案、全局方案定义、功能清单 | 建立 `USS -> MOD -> FR -> 原型 -> PRD` 桥接关系 |
| `04_模块功能映射表.md` | 需要按模块聚合功能时 | 功能清单、FR桥接总表 | 建立模块与功能的聚合视图 |
| `99_跨模块设计与冲突处理/*.md` | 发现跨模块冲突、口径不一致、边界争议时 | 模块方案、全局方案定义、评审结论 | 保留正式裁决与冲突处理记录 |

## 5. 推荐使用顺序

建议按以下顺序阅读和维护：

1. 先读取 `<PROJECT_ROOT>/02_一号仓库/03_需求分析/` 的正式输入。
2. 先建立 `00_产品解决方案总览.md` 的模块划分、协作分工和范围骨架。
3. 再按模块建立 `MODxx-模块名/`。
4. 再在各模块内补 `USS-*` 及模块级流程、规则、实体属性、权限、导航、异常闭环设计。
5. 再把跨模块共性收口到 `02_全局方案定义/`。
6. 再回填根层桥接文件：`01_产品功能清单.md`、`03_FR桥接总表.md`、`04_模块功能映射表.md`。
7. 若存在模块边界、实体口径、状态规则冲突，再进入 `99_跨模块设计与冲突处理/` 形成裁决记录。
8. 最后回写 `00_产品解决方案总览.md` 的进度、风险和进入原型阶段门禁结论。

## 6. 事实归属规则

本目录内部的事实归属固定如下：

1. 单故事范围内的来源追溯、细粒度场景和故事目标，以对应 `USS-*.md` 为准。
2. 模块内部的流程、规则、实体、属性、状态、权限、导航、异常闭环，以对应模块方案包为准。
3. 跨模块统一状态、统一属性口径、统一字典、统一权限边界、统一导航协同和统一集成约束，以 `02_全局方案定义/` 为准。
4. 功能点桥接关系、`FR-*` 预分配编号、优先级和版本纳入范围，以根层桥接文件 `01_产品功能清单.md`、`03_FR桥接总表.md`、`04_模块功能映射表.md` 为准。
5. 发生模块边界冲突、实体口径冲突、规则口径冲突时，以 `99_跨模块设计与冲突处理/` 的正式裁决记录为准。

建议优先级：

`99_跨模块设计与冲突处理 > 02_全局方案定义 > MODxx-模块名 > USS-*`

## 7. 方案阶段与版本治理边界

本目录与版本治理的边界，建议按以下方式理解：

1. 本目录负责把“当前版本候选范围”设计成可进入原型和 PRD 的方案真源。
2. 本目录不负责替代一号仓库确认当前版本是否纳入、是否删除、是否转下一版本。
3. 若在方案阶段发现：
   - 当前需求是否纳入本版本仍未裁决
   - 需求范围新增或删除已经影响版本边界
   - 当前变化本质上已属于下一版本
   应先回一号仓库或零号仓库处理，不应继续把它写成“当前版本方案已稳定”。
4. 若当前版本已经冻结，后续正式变化不得伪装成本目录中的普通方案迭代，应改走产品基线正式变更链路。

## 8. 进入门禁

进入本目录开展正式方案设计前，至少应满足：

1. `<PROJECT_ROOT>/02_一号仓库/03_需求分析/` 已形成正式需求输入。
2. 本轮范围内的 `US / URD` 已稳定，不再处于待确认状态。
3. 已能明确划分模块、用户故事和版本范围。
4. 不存在“是否属于当前版本 / 是否应转下一版本”的关键争议。

若以上条件不满足，应先回到一号仓库继续收口，不应直接开始二号仓库方案设计。

## 9. 进入原型阶段门禁

方案阶段内容满足以下条件后，才建议进入 `02_产品原型/`：

1. `00_产品解决方案总览.md` 已形成。
2. 本轮范围内的核心模块方案已完成。
3. `02_全局方案定义/` 已收口跨模块状态、规则、实体、属性、字典、权限和导航原则。
4. `03_FR桥接总表.md` 已建立 `USS -> MOD -> FR` 的正式桥接关系。
5. 每个核心功能点都已具备明确的页面类型方向和入口关系。
6. 不存在未裁决的关键跨模块业务冲突。
7. 不存在影响版本边界的关键争议。

## 10. 强制边界

1. 不在本目录内复制一号仓库正文。
2. 不在本目录内直接生成正式 `PD-*` 页面设计文档。
3. 不在本目录内直接生成正式 `FR-*` 正文文档，但允许在桥接文档中预分配 `FR-*` 编号。
4. 不得把跨模块规则只散落在局部 `USS-*` 或单一模块文档中而不回写 `02_全局方案定义/`。
5. 不得跳过本目录直接从需求分析进入原型或 PRD。
6. 若当前变化已经影响版本纳入范围、版本归属或冻结边界，不得由本目录直接裁决为“继续下游”，应先回一号仓库或零号仓库补版本真源。
