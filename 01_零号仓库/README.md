# 零号仓库

## 1. 仓库定位

`01_零号仓库/` 是项目全过程的横向项目管理仓与治理真源仓。

它不承担一号、二号、三号、四号仓库的正文设计职责，而是负责把项目级边界、环境、范围、节奏和关键约束写成可追溯、可持续回写的正式真源。

一句话理解：

**零号仓库负责维护项目级管理真源，而不是串行阶段正文。**

## 2. 当前结构

```text
01_零号仓库/
├── README.md
├── .claude/
├── .agents/
├── 01_项目核准证/
├── 02_项目环境/
├── 03_产品需求清单/
└── 04_产品路标/
```

各目录职责如下：

- `01_项目核准证/`
  - 记录项目立项背景、适用主体、目标边界、阶段范围、职责前提和准入结论
- `02_项目环境/`
  - 记录 Git、环境、权限、账号、协作机制、AI 插件和工具准备情况
- `03_产品需求清单/`
  - 记录产品需求池、首期范围、非首期范围、优先级、项目级回写状态和正式版本需求清单
- `04_产品路标/`
  - 记录阶段节奏、里程碑、版本规划、关键依赖、偏差纠正动作以及全部正式版本主控信息

## 3. 产物分层口径

零号仓库中的正式产物，建议按四类理解：

1. 启动准入真源
   - `01_项目核准证/`
   - 回答“项目为什么做、做到哪里、当前能否进入正式推进”
2. 环境协作真源
   - `02_项目环境/`
   - 回答“仓库、权限、协作和 AI 运行前提是否已经具备”
3. 范围治理真源
   - `03_产品需求清单/`
   - 回答“产品需求池、首期范围、非首期范围和优先级如何持续治理”
4. 节奏治理真源
   - `04_产品路标/`
   - 回答“项目按什么节奏推进、里程碑如何变化、哪些调整需要项目级回写”

一句话理解：

**项目核准证和项目环境回答能否推进，需求清单和产品路标回答推进中如何治理。**

## 4. 真源规则

零号仓库内部同类信息的优先级，建议按以下顺序理解：

1. 启动准入边界、适用范围、角色前提，以 `01_项目核准证/` 为准
2. 环境、权限、账号、AI 运行前提和协作准备，以 `02_项目环境/` 为准
3. 产品需求池、首期范围、优先级口径，以 `03_产品需求清单/` 为准
4. 节奏、版本和里程碑，以 `04_产品路标/` 为准

如果多个文档对同一事实描述不一致，必须回到上述主文件修正，不能在其他仓库说明文档中各写各的口径。

## 5. 输入来源与横向治理关系

零号仓库的输入分成两类：

1. 启动准入输入
   - 用于形成 `01_项目核准证/` 与 `02_项目环境/`
   - 来自项目立项、项目经理组织、产品经理准备、技术负责人和协作机制确认
2. 过程治理回写输入
   - 用于持续更新 `03_产品需求清单/` 与 `04_产品路标/`
   - 主要来自一号仓库、二号仓库阶段收口后的正式回写

零号仓库与一号、二号、三号、四号仓库之间，不是串行上下游关系，而是横向治理与持续回写关系。

建议按以下方式理解：

1. 对一号仓库
   - 提供项目边界、环境前提和启动约束
   - 在一号仓库阶段结束后，接收产品需求池与版本需求范围回写
2. 对二号仓库
   - 提供版本范围、阶段目标和关键依赖约束
   - 在二号仓库产品基线结束后，接收产品路标与版本节奏回写
3. 对三号、四号仓库
   - 提供项目环境、里程碑和项目级协作约束
   - 若项目边界或环境发生重大变化，接收对项目核准证或项目环境的回写

## 6. 推荐使用顺序

若在零号仓库中新增、改写或补写正式文档，建议按以下顺序执行：

1. 先看 `<TOOL_REPO_ROOT>/09_DIC研发方法论/README.md`，确认阶段定义与角色边界
2. 再看 `<TOOL_REPO_ROOT>/06_工作规范/03_项目管理规范/` 与 `<TOOL_REPO_ROOT>/06_工作规范/05_产品设计规范/`
3. 再从 `<TOOL_REPO_ROOT>/07_公共模板库/02_零号仓库模板/` 选择对应模板
4. 如需 AI 协作，再进入 `<TOOL_REPO_ROOT>/08_AI工作站/`
5. 最后把正式产物落到本仓库对应目录

版本补充说明：

1. 当前工作版本和当前工作分支，以 `04_产品路标/00_版本总表.md` 为准。
2. 单版本身份、里程碑和正式承接关系，以 `04_产品路标/VER-vX.Y.Z_版本卡.md` 为准。
3. 单版本项目级纳入范围，以 `03_产品需求清单/VDL-vX.Y.Z_版本需求清单.md` 为准。
4. 项目级滚动需求治理，以 `03_产品需求清单/00_产品需求池.md` 为准。
5. 若开始新版本，应先在零号仓库完成新版本身份建立，再进入一号仓库和二号仓库。
6. 若只是修正已冻结或已发布版本，不应直接当成新版本推进，应结合一号仓库版本变更确认和二号仓库产品基线，判断是否进入 `hotfix/vX.Y.Z`。

## 7. 推荐工作链路

零号仓库建议按以下横向治理链路推进：

```text
项目启动
-> 项目核准证
-> 项目环境
-> 一号仓库推进并结束
-> 回写产品需求池
-> 二号仓库推进并完成产品基线
-> 回写产品路标
-> 边界或环境变化时回写核准证/项目环境
-> 下一版本继续滚动更新
```

版本治理补充理解：

1. 新版本启动时
   - 先回写 `00_版本总表.md`
   - 再建立 `VER-vX.Y.Z_版本卡.md`
   - 再建立 `VDL-vX.Y.Z_版本需求清单.md`
2. 当前版本基线冻结后若发生正式变化
   - 零号仓库不直接替代一号、二号仓库完成变更分析
   - 但需要持续保持版本状态、版本范围和项目级节奏口径一致
3. 当前版本若进入修复型承接
   - 应在项目级口径上明确这是当前版本修复，而不是下一版本扩展

- `01_项目核准证/`、`02_项目环境/`
  - 通常在项目正式推进前形成最小可用版本
  - 项目推进中如边界、角色、权限、环境变化，也必须持续修订
- `03_产品需求清单/`、`04_产品路标/`
  - 属于项目全过程持续治理真源
  - 不要求一次性定稿，但要求随着项目推进持续回写

## 8. 推荐正式产物

零号仓库建议至少形成以下正式产物：

1. 项目核准证
2. 项目环境说明
3. 产品需求清单
4. 产品路标

## 9. 项目启动前的最小门禁

项目正式进入各正文仓库前，建议至少确认：

1. 项目核准与适用范围已明确
2. 项目环境、账号、协作和 AI 运行前提已准备
3. 当前版本或当前阶段的首期范围已初步登记
4. 产品路标和阶段节奏已形成初版
5. 需要在一号、二号、三号、四号仓库重点核查的问题已有初步列表

## 10. 强制边界

- 零号仓库不是需求分析正文主仓
- 不在零号仓库内沉淀正式方案设计、原型设计、PRD 或研发实现内容
- 不用零散会议纪要替代正式项目结论
- 未确认的信息必须显式标记为待确认，不得直接写成既成事实
- 正式产物应落在既定目录，不要写成漂浮的临时说明文件
- 一号、二号、三号、四号仓库若发生项目级变化，不得只在各自正文仓处理，必须回写真源到零号仓库

## 11. 初始化后优先补充

若由模板初始化真实项目仓库，建议优先补：

1. `01_项目核准证/`
2. `02_项目环境/`
3. `03_产品需求清单/`
4. `04_产品路标/`
