# 三号仓库

## 1. 仓库定位

`04_三号仓库/` 是项目技术方案主仓。

它位于二号仓库与四号仓库之间，负责把产品基线转化为可研发、可验证、可交接的技术方案输入。

当前三号仓正式采用“全局总控在前、模块技术包为主、跨模块专项单列”的组织方式：

1. 版本级范围冻结、系统级、统一约束类内容放在全局层。
2. 模块级前端、后端、数据库、风险、实施和交接内容，统一收在模块技术包内。
3. 跨多个模块共同成立的接口、集成、对账补偿和公共能力专题，单独放在跨模块专项层。

## 3. 主要产物

1. 技术方案门禁与评审事实
2. 当前版本需求范围与技术承接清单
3. 系统级总体技术方案与统一约束
4. 按模块归档的技术方案包
5. 跨模块专项设计与公共能力专题
6. 模块级实施编排、页面级实施清单、编码与单元测试输入和研发交接说明
7. 面向 `AI Code / Superpowers` 的结构化研发输入

## 4. 上游输入

三号仓库的主要输入来自二号仓库，建议至少承接以下内容：

1. 产品解决方案总览
2. 页面设计与原型真源
3. PRD 与护栏设计
4. 产品基线
5. 关键对象、状态、权限、接口定义

说明：

1. 三号仓库不是重新发明产品设计结论的地方。
2. 若技术方案阶段发现二号仓库前置假设不成立，应显式回流修订上游真源。

## 7. 推荐正式产物清单

三号仓库建议至少形成以下正式产物：

1. 版本级技术方案门禁记录与评审单
2. 当前版本需求范围与技术承接清单
3. 总体技术方案
4. 技术方案到产品基线的映射说明
5. 模块技术总览
6. 模块前端技术方案
7. 模块后端技术方案
8. 模块数据库设计方案
9. 模块技术风险与验证结论
10. 模块实施编排总控与页面级实施清单
11. 模块编码实现与单元测试输入
12. 模块研发验证与交接说明
13. 跨模块外部提供接口设计
14. 跨模块外部引用接口设计
15. 跨模块系统集成与对账补偿设计
16. 跨模块专项与公共能力复用评估结论
17. 面向代码仓汇编的 `AI_CODE_INPUT` 真源索引与模块输入基础

补充说明：

1. 一个真实业务模块，建议在 `02_模块技术方案/` 下形成一个完整技术包。
2. 页面级实施清单不在根层散放，应挂在对应模块目录下。
3. 编码与单元测试输入建议挂在对应模块目录下，用于直接支撑 AI Code。
4. 跨模块事项若无法归到单个模块，应进入 `03_跨模块专项/`。
5. 若项目后续使用 `Superpowers` 执行 AI Code，建议由代码仓按模块汇编 `AI_CODE_INPUT/`，而不是让执行引擎直接扫描整个项目仓库。

## 8. 与四号仓库的交接关系

三号仓库向四号仓库提供的不是代码，而是“可执行的研发输入”。

建议至少明确以下交接项：

1. 研发设计的整体分解思路
2. 前后端模块边界和内部接口落地路径
3. 数据库设计、SQL 生成和数据变更约束
4. 外部提供接口、外部引用接口和系统集成约束
5. 已验证风险与未闭环风险
6. 当前模块编码实现与单元测试输入
7. 需要持续跟踪的实现约束
8. 当前模块范围的研发实施输入与验证输入

## 9. 进入四号仓库前的最小门禁

进入四号仓库前，建议至少确认：

1. 总体技术方案已形成
2. 当前模块技术包已形成最小闭环
3. 关键前后端实现路径已明确
4. 数据库设计已可稳定推导 SQL 与数据变更脚本
5. 内部接口已可稳定支撑前后端研发落地
6. 命中的外部接口、系统集成和对账补偿专题已形成
7. 关键技术风险已有验证或兜底策略
8. 与二号仓库产品基线的关键追溯关系已明确
9. 当前范围已有正式技术方案门禁与评审事实
10. 当前版本需求范围与技术承接清单已形成
11. 交付给四号仓库或 AI Code 的研发输入已经结构化整理
12. 模块研发验证与交接说明已形成
13. 若交付目标包含 `AI Code / Superpowers`，当前范围已可稳定汇编为 `AI_CODE_INPUT/`

## 10. 不应承载的内容

1. 不替代二号仓库重写产品设计真源
2. 不直接承接最终测试、上线和运维交接结论
3. 不在本仓库内复制公共规范、模板和 AI 工作站正文
4. 不把纯实现日志替代技术方案正文

## 11. 一句话说明

**三号仓库负责把产品设计结果转化为按模块收口、可执行、可交接的技术方案。**
