## 2. 事务模型（FR-008-P2 原子留痕）

1. 连接管理：每请求一连接（`sqlite3.connect(path, isolation_level=None)` 手动事务），连接级 `PRAGMA foreign_keys=ON`（M01 §7）。
2. 修订路径 **PUT /api/rules/{id}** 是唯一更新 rule 状态的代码路径，其在**同一个显式事务**内执行两条 DML：

```python
with conn:                      # 事务边界：块内任一异常 → 自动 ROLLBACK
    conn.execute("UPDATE rule SET rule_status=?, basis_text=?, operator=?, updated_at=? WHERE id=?", ...)
    conn.execute("INSERT INTO change_log(rule_id, old_status, new_status, basis_text, operator, changed_at) VALUES(...)", ...)
```

3. SQLite 单文件单写者：两条语句同连接同事务，提交原子——**不存在**「规则已更新而留痕未写」或反之的中间态可被任何观察者读到（含进程崩溃场景：未 COMMIT 的事务整体不落盘，EX-FR008-03 回滚语义由引擎保证）。
4. 事务外的两个前置拦截不破坏原子性：404（规则不存在）与 422（同状态，FR008-P1）都在 BEGIN 前只读判断，此时未发生任何写。

## 3. 无「仅更新不留痕」端点——逐端点枚举证明（AT-FR008-005 证据）

### 3.2 逐项排除结论

1. **无「仅更新不留痕」端点**：枚举中唯一更新状态的 #8 强制同事务写 change_log；不存在第 9 条业务路由（Task-009 验收含路由数断言 `len(app.routes) == 8 + 框架内置`）。
2. **change_log 无编辑/删除 API**：#5 仅 GET；change_log 不出现在任何其他方法的路径/表单里（GBR-003/FR-008-P4 API 面证明）。
3. **UI 无入口**：PD-003 只读时间线、PD-004 仅有登记/修订（M04 §5），无删除规则、无批量、无导入（FR-008 §1.3 排除项照单实现为零）。
4. **库级第二道防线**：即便绕过 API 直连 SQLite 执行 `UPDATE/DELETE change_log`，触发器 `trg_change_log_no_update/no_delete` RAISE ABORT（M01 §4.1）——四号仓库可用 sqlite3 CLI 断言触发器存在与生效。
5. **种子脚本不改状态不造痕**：seed.py 仅 INSERT（M05），初始化不在「留痕无绕过」语义内（系统外建库行为，留痕声明于本节）。

## 4. 读一致性与即时生效（GBR-005）

1. 三视图（PD-001/002/005）与时间线均为**读时计算**：不缓存合并态、不落中间表（M01 §2.4 拒绝冗余列）→ 修订 COMMIT 后下一次查询即新口径，无失效逻辑可出错。
2. change_log 与 rule 的读一致性：时间线读 change_log（事实表），视图读 rule（现状表），二者由同一事务写入——不存在「视图已新态、时间线缺记录」的窗口（§2.3）。

## 6. 供四号仓库的断言清单（测试设计输入）

1. API 面：对 8 路由之外的写尝试（POST /api/changes、DELETE /api/rules/{id}、PATCH …）断言 405/404。
2. 事务面：修订成功后 `sqlite3 minhuo.db "SELECT COUNT(*) FROM change_log WHERE rule_id=<id>"` 增量为 1 且 rule.updated_at 变化；构造失败（如 basis_text 超长触发 CHECK）断言两者都不变。

4. 一致面：同一条目四端点（overview 计数/rules/matrix/{code}/rules/search）合并态与 conflict 逐值相等（AT-FR003-005）。
